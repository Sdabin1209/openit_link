# 0001. 받는 쪽은 WSGI 앱 하나로

- 상태: 채택(2026-10-30)
- 맥락: 영역마다 받는 쪽 HTTP 서버를 따로 만들어 401/403 구분, 요청의 계약 검증, 오류 형식이 갈라졌다(2026-10-30 독립 검토, 참조 서버도 같은 쪽으로 틀림). D118로 통신 기반을 한 곳에 둔다.
- 결정: 표준 WSGI(PEP 3333) 앱 `App`과 선언형 `Route`. 프레임워크를 들이지 않는다.
- 왜: 영역 서버 7곳이 모두 waitress(WSGI) 위에서 돈다(2026-10-30 확인). 같은 인터페이스면 영역이 서버 기동 코드를 바꾸지 않고 앱만 갈아 끼운다. 상태 코드 표는 CONVENTIONS 9절, 401/403은 D106(RFC 9110 15.5.2, RFC 6750 3절).
- 검토한 대안: (1) Flask/FastAPI — 의존이 커지고 영역 7곳의 서버 코드를 다 바꿔야 한다. (2) 영역마다 지금처럼 — 규약이 갈라진 원인이라 버린다. (3) 계약 패키지 안에 서버 기반 — 통신 코드를 고칠 때 계약 버전이 바뀐다(명세와 런타임을 섞지 않는다).
- 결과: 규약을 한 곳에서 시험한다. 영역의 `link_*`는 경로·타입 변환만 담는다. 감수: 경로 매칭은 단순 패턴(`{이름}`)뿐이다.
- 되돌리는 조건: 영역 하나라도 WSGI가 아닌 서버가 필요해지면(예: 스트리밍) 그 경우만 따로 다룬다.
- 0.2.0(추가만, 0.1.0 사용 그대로 동작): 스키마 이름에 "이름#/$defs/X", 쿼리 스키마, 토큰 표 값에 {role, actor}(Request.actor), 토큰 상수 시간 비교(hmac.compare_digest, 모든 후보를 끝까지), bytes 반복자 응답(스트리밍), 원래 경로(REQUEST_URI)로 매칭해 %2F 보존, 405에 Allow(RFC 9110 15.5.6). 영역 변경 요청 question-authoring CR-0008, synthetic-data CR-S-002.
- 0.3.0(추가만): Route.stream_body(Request.stream, 수 GiB 게시), App(authenticate=...) 토큰이 없을 때의 추가 인증(내부망 X-Openit-Device, ADR 0012), HttpError(BoundaryError, 머리글)로 Retry-After 등, 엄격한 JSON(I-JSON RFC 7493: UTF-8·중복 키·짝 없는 서로게이트 거부·중첩 상한 64, 넘으면 400 — 재귀 한도로 500이 나던 것), ready_public으로 인증되지 않은 /readyz에는 사유를 감춘다. 요청: survey-service CR-link-001, model-lab CR-L013, model-runtime CR-007. 인증 실패 횟수 제한·동시 처리 상한은 표준 WSGI 겉옷(middleware)으로 영역이 App을 감싸 둔다(라이브러리 밖, 규약이 아니라 서버별 방어).
- 0.4.0: 405·413 본문도 BoundaryError(INVALID_RECORD, details.http_status — CONVENTIONS 9절 "실패는 BoundaryError 레코드"; 0.3.0까지 {"message"}였던 것은 결함), App(on_result=…) 감사 훅(경로가 있는 모든 요청의 결과를 성공·거부 모두 한 번씩, 요청마다 따로; 훅 예외는 응답을 바꾸지 않는다). 요청: release-gate CR-0011.
- 상수: 본문 기본 상한 1 MiB — 측정값이 아니라 판단(계약 요청 레코드 하나), 큰 본문 경로는 Route.max_body로 늘린다. 전송 한도(413)는 인증보다 먼저 본다(CONVENTIONS 9절 2.2.2).
